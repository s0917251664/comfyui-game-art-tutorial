# 需求 brief 與驗收

跨工具共用的工作方法：釐清目標、來源與參考圖的職責、修改與保留、版本、分階段、人工驗收。它不執行生成，也不假設任何引擎有特定控制能力。task、參數、能力 gate 不在這裡，查 `generate.py <task> --help` 與 `gameart.py run show <id>`。

## 先分清工作與執行者

先判斷是靜態圖、短動態影片，還是本機素材處理；再確認使用者要整理需求、實際執行，或兩者都要。執行路線沿用使用者選的，不因缺能力自行換引擎。

| 路線 | 判斷依據 |
|---|---|
| 本機 ComfyUI | 只有使用者選這條才交給 [comfyui-run](../../../skills/comfyui-run/SKILL.md)。圖片與影片是不同能力，不能用圖片 task 代替影片 task |
| 平台原生圖片工具 | 本次會話確有工具才用；先核對當下 schema，不明就交付 brief。不是外部付費 API，目前也沒有接外部付費服務 |
| 本機像素、音訊、影片處理 | 遮罩合成、換色、比較、Alpha 檢查、物件組裝、去背打包是各自獨立的本機職責，不是生成模型能力 |
| 影片與特效 | 平台圖片工具不等於影片工具；沒有已接入的影片能力時只整理 brief |

ComfyUI 的 task、seed、denoise、ControlNet、Alpha 遮罩、逐像素保留行為，都不能直接對應成平台功能。局部保留的差別：ComfyUI 生成仍會漂移，確認過的遮罩加確定性合成才能驗證遮罩外像素；平台語意編修不保證逐像素保留。

## 共用需求整理

只收集完成需求所需的資訊，已有的答案沿用；關鍵來源、目標或修改範圍判斷不了才問。

1. **目標與用途**：要做的素材或畫面、遊戲內用途、格式／尺寸／比例／透明需求。區分概念探索、候選製作、定稿修改、交付整理。
2. **輸入素材與職責**：逐一標明來源（編修目標）、角色身份、姿勢或結構、外觀或材質、背景、遮罩預覽、候選版本。一張圖可有多種用途，但要說明優先順序；參考圖只提供指定資訊，不自動帶入其中的人物、姿勢或背景。參考圖板只供人看，引擎不會把板面解讀成多張獨立參考。
3. **本輪修改與保留**：新增、刪除、改變什麼；必須維持的特徵、輪廓、數量、姿勢、構圖、色彩、背景、文字、透明邊界。把「希望模型遵循」和「由遮罩合成等確定性步驟保留」分開寫，只有實際可用的機制才可承諾像素保留。
4. **分階段與版本**：改動能分開驗收、或前一步決定後一步時才拆階段。每階段記明輸入版本、產出候選、檢查點。未經使用者選定的候選不自動成為下一階段母版。
5. **交付與驗收**：寫成可觀察條件（需求命中、禁止變動項、形狀與空間關係、視覺缺陷，以及格式、尺寸、Alpha、影格、循環接縫、音訊）。技術檢查、agent 的內容觀察、使用者的接受決定三者分開記錄（[R1](../rules/candidate-review.md)）。

交接時給一段精簡的內容描述，保留使用者指定的詞句；提示更長不必然更好。引擎專屬的 token、negative、模型參數由執行端處理，不寫進共用需求。

## 版本狀態

只用有依據的狀態：`candidate`（待看）、`accepted`、`rejected`（使用者明確決定）。`observed` 等工具檢查紀錄另列，不混入素材狀態。新輸出不繼承舊版的接受狀態。圖片預設留 `*.result.json` 技術 manifest，使用者明確決定後才用 `gameart.py review accept|reject --by <使用者>` 記錄（綁輸出 hash）。agent 不替使用者決定。

## 產後人工觀察

借用圖片評測的維度當檢查問題，不轉成自動評分：

- **需求符合度**：指定的修改是否出現、呈現方式對不對。
- **局部性**：改動是否集中在預期區域；區分生成變動與後續遮罩合成的結果。
- **保留項**：臉、輪廓、姿勢、裝備、文字、背景有沒有漂移。
- **空間關係**：物件、肢體、配件的位置與方向。
- **交付條件**：尺寸、格式、透明通道這類可機械檢查的條件。

`compare` 看像素差異但不懂語意，`asset-audit` 只查 Alpha／尺寸／碰邊。工具數據、人工觀察、美術決定分開寫。

## 製作方法

### 物件系列與展示

已有母圖、只要展示或精確重複時，直接確認原檔、尺寸、Alpha，再選確定性工具；不為排版重新生成物件。要製作新物件或系列變體時：

1. 先做一件代表素材：寫明共通身份與結構、可變欄位（顏色、材質、稀有度）、不可變動項；驗收外形、比例、透明邊界、風格與遊戲用途。
2. 確認系列規則後再擴展；逐件檢查差異是否只落在預期欄位。同一批生成不代表系列一致。
3. 展示目的有三種：scene（單件放進背景）、sheet（並列檢視）、pattern（重複同一母圖樣）。它們是交付目的，由本機 Pillow 確定性合成；平台若用生成模型重新構圖，會重畫內容，不能承諾原素材像素、數量或排列。
4. 交付前保存代表素材與每個變體的來源；展示合成圖不是透明素材，圖樣重複不等於無縫。細節見 [物件組裝](object-design-workflows.md)。

### 靜態與短動態特效

先分清交付的是靜態特效素材、生成式短動態、綠幕影片、既有片段合成，還是來源影片的遮罩／圖層處理，各自對應不同工具。brief 要寫：外觀與用途、動態的起承結與節奏、循環時首尾如何銜接、背景與遮擋關係、鏡頭是否移動、交付形式。規格（解析度、FPS、時長、Alpha）由接手工具確認，不預設固定值。

驗收看：效果是否符合描述、運動是否穩定、主體是否漂移或變形、背景污染、邊緣與遮罩品質、首尾接縫。影片的技術驗證只代表容器與編碼通過，不代表特效美術接受；除非走過透明輸出後處理，不承諾影片候選能直接成為透明特效或 sprite sheet。

### 同一角色的動作集合

1. 由美術確認一張角色母圖，記下身份錨點（臉、髮型、服裝、配色、裝備、比例）；未接受的候選不取代母圖。
2. 先選最能暴露身份、姿勢、道具或循環問題的代表動作；整理動作意圖、起姿與方向、鏡頭、片長。
3. 代表候選逐項驗收（身份、動作可讀性、姿勢與道具、構圖、起訖與接縫）；不合格先由使用者決定調整方向或停止，再擴展。
4. 擴展成動作表，每支各自驗收；一支通過不代表整組通過。
5. 逐支選版交付，保留其他候選供比較。編排細節見 [動作組](../animation/workflow.md)。

## 影片 brief 欄位

效果主體、動作與鏡頭、起訖狀態、背景與遮擋、時長與畫面尺寸／FPS、是否循環與接縫、音訊、圖層順序、交付格式。這些是需求欄位，不表示工具已支援。靜態特效圖、生成短片、綠幕合成、影片遮罩傳播、2D 圖層組合是不同工作，逐項選擇相符的工具。

## 平台圖片工具的實測範圍

2026-10-05 在當前會話用平台原生圖片工具各做一次文字生圖與單張來源圖編修（透明背景的藍色魔法藥水瓶改成紅色液體），兩張都是 1254×1254 RGBA。瓶身構圖目視接近，但玻璃高光、液體細節與部分 Alpha 有變化，藍版可見內容碰到畫布邊界。結論：語意編修能完成顏色變更，但不能承諾其他細節或像素保留。這次沒有用遮罩，也沒有驗證多參考、其他平台或影片；兩張都只是待驗收的候選。

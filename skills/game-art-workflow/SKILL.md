# 遊戲美術 AI 共用工作流程

本技能整理跨工具可共用的工作方法：釐清目標、來源與參考圖職責、修改和保留範圍、版本關係、分階段計畫及人工驗收。它不執行圖片或影片生成，不假設任一引擎有特定控制能力。

需要專案現有工具職責或平台差異時，按需查[職責盤點](references/responsibilities.md)；物件系列、靜態／短動態特效和角色動作編排時，按需查[製作方法](references/production.md)。一般圖片編修 fast path 只需本技能，不先讀完整職責資料或作品案例。整個資料夾可單獨移植；不依賴其他 repo 文件或本機 runtime。

## 按需閱讀

| 需求 | 需要時讀取 |
|---|---|
| 多參考編修、局部修改、角色／結構保留 | 本技能的「共用需求整理」；選擇執行工具後讀該 executor 的技能 |
| 物件系列、展示或圖樣重複 | [production.md](references/production.md) 的物件系列段 |
| 靜態特效或短動態 VFX | [production.md](references/production.md) 的 VFX 段；再讀相符的圖片或影片 executor |
| 同一角色一組遊戲動作 | [production.md](references/production.md) 的角色動作段；執行時再讀圖片／影片技能 |
| 需要比較現有工具責任、依賴或驗證狀態 | [responsibilities.md](references/responsibilities.md) |

選用**平台原生圖片工具**只表示本次平台實際提供的工具；不要將其與外部付費 API／CLI 混為一談。外部付費 API／CLI 不屬於目前接入能力；本工作流程不安裝套件、不讀取 API key，也不假定使用者有付費權限。若未來有明確接入，需由獨立 executor 文件定義其使用方式。

## 先分清工作與執行者

先把需求判斷為靜態圖片、短動態／影片，或本機素材處理。再確認使用者要的是整理需求、實際執行，還是兩者都要。

- **ComfyUI 專案產線**：只有在使用者選擇本機 ComfyUI 路線時，才交給該產線入口處理 task 選擇、機器能力 gate、模型與輸入契約、執行及技術檢查。圖片與影片是不同能力，不能用圖片 task 代替影片 task。不得自行拼接未登記的 graph 或把平台能力算成本機驗證。
- **平台圖片 Agent**：只有當目前會話提供可用的圖片生成／編修工具時，才由該平台路線執行。先核實當下工具 schema 和可用輸入，再按其能力整理及提交；能力不存在或不明時，交付 brief 供人使用，不猜 API、工具名稱、付費權限或控制參數。
- **本機素材工具**：遮罩繪製、RGBA 合成、比較、換色、透明度檢查、參考板與固定 Core 排版等，是各自獨立的本機職責。確認程式、依賴和輸入契約後才可執行；不把它們描述成生成模型能力。
- **影片與特效**：平台圖片工具不等於影片工具。影片、循環特效、片段合成、遮罩追蹤及圖層合成需各自有明確執行能力；沒有已接入的影片工具時，只整理需求與驗收 brief。

執行路線沿用使用者選擇或呼叫端已確定的預設，不因缺能力自行換引擎。交給對應 executor 時傳遞已整理的 brief、原始素材及版本識別，不必先載入整份職責盤點。共用流程只定義需求和驗收，不覆蓋工具專屬的能力 gate、輸入限制或實測狀態；執行者回報能力缺口及實際產物，再依本技能檢查內容。

## 共用需求整理

只收集完成需求所需的資訊；已有答案沿用，不為填表而追問。關鍵來源、目標或修改範圍無法判斷時，先問清楚。

1. **目標與用途**：描述要做的素材或畫面、遊戲內用途、所需格式／尺寸／比例／透明需求，以及這次要回答的主要問題。區分概念探索、候選製作、定稿修改與交付整理。
2. **輸入素材與各自職責**：逐一標明原始來源（source/edit target）、角色身份參考（character）、姿勢或結構參考（pose/structure）、外觀或材質參考（appearance）、背景、遮罩或範圍預覽（mask preview）、候選版本（candidate）。一張圖可有多種用途，但要說明優先順序；參考圖只提供指定資訊，不自動引入其中其他人物、姿勢、物件或背景。參考圖板只供人檢視，不能假定引擎會把板面解讀成多張獨立參考。
3. **本輪修改與保留**：說明這輪要新增、刪除或改變什麼；列明必須維持的角色特徵、輪廓、數量、姿勢、構圖、色彩、背景、文字、透明邊界或其他條件。將「希望模型遵循的內容」和「由遮罩合成等確定性步驟保留的內容」分開寫；只有實際可用的工具機制才可承諾像素保留。
4. **分階段與來源版本**：只有改動能分開驗收、或前一步結果會決定後一步時才拆階段。每階段記明輸入版本、工作、產出候選、檢查點和下一步依據。保留檔案／版本識別；未經使用者選定的 candidate 不得自動成為下一階段母版。使用者可選任一候選、要求沿用既有來源或停止。
5. **交付與驗收**：把驗收寫成可觀察條件，包含需求命中、禁止變動項、角色／形狀／空間關係、視覺缺陷，以及格式、尺寸、Alpha、影格、循環接縫、音訊或合成等適用項目。區分引擎／檔案技術檢查、Agent 的可見內容觀察與美術使用者的接受決定。工具成功、提示詞遵循或技術 pass 都不能代替美術接受。

交接時提供一段自然、精簡的內容描述，保留使用者指定的精確詞句；提示更長不必然更好。引擎專屬 token、negative 欄位和模型參數由 executor 依契約處理，不寫入共用需求當作通用控制。單次需求只傳必要欄位，不要求每案建立完整表格或資產紀錄。

## 版本狀態與回報

對每個實際產物保留可識別的檔名或版本，並在需要時記錄其來源、使用的參考、提示／要求、工具路線、技術觀察和內容驗收。素材版本只使用有依據的狀態：`candidate`（待看）、`accepted`（使用者明確接受）、`rejected`（使用者明確拒絕）。`observed` 等工具檢查紀錄另列，不混入素材驗收狀態。不要推測或替使用者決定狀態，也不要讓新輸出繼承舊版本的接受狀態。

回報時說清楚交付物、完成了哪些檢查、仍有何不確定，以及需要使用者選擇的候選。沒有執行工具時，明確交付 brief／計畫，不暗示已有生成結果。

## 影片與特效專用說明

影片 brief 還要描述效果主體、動作／鏡頭、起訖狀態、背景與遮擋關係、時長、畫面尺寸／FPS、是否循環、循環接縫、音訊、圖層順序及預期交付格式。這些是需求欄位，不表示工具已支援或通過驗證。靜態特效圖、生成短片、綠幕合成、影片遮罩傳播及 2D 圖層組合是不同工作；逐項選擇相符工具並依其契約執行。不可把候選影片描述成可直接匯入遊戲引擎的透明序列、Sprite Sheet 或已拆出的乾淨 VFX。

此共用流程不規定生成重試次數。執行者需遵守所選工具的行為和當下平台規則；不可盲目重送、覆蓋候選，或以另一條工具路線悄悄替代原需求。
